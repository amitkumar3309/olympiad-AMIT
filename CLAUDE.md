## Project Purpose

AMIT Maths Olympiad is a national-level math competition web platform: student registration, an online exam, results, certificates, a leaderboard, and an admin panel for managing students/questions. Founder/brand name referenced throughout the UI: "Amit Kumar".

## Technology Stack

- **Frontend**: React 19 + TypeScript, Vite 8, `react-router-dom` v7, `chart.js` / `react-chartjs-2`, CSS Modules (no UI framework/Tailwind). Linter: `oxlint`.
- **Backend**: Node.js + Express 5 + TypeScript, run via `tsx`. One AI dependency: **`@google/genai`** (question drafting only — see the Milestone 20 ADR, which supersedes Milestone 17's decision against an SDK; it is `require`d rather than `import`ed for a packaging reason documented at the top of `services/geminiQuestionGenerator.ts`). Modular structure since Milestone 1 (`config/`, `db/`, `lib/`, `middleware/`, `models/`, `routes/v1/`, `validation/`). Uses `zod` (validation), `pino` (logging), `helmet`, `express-rate-limit`. Linter: `eslint` + `typescript-eslint`. Tests: `vitest` + `supertest`.
- **Database**: MongoDB via Mongoose.
- **Auth**: short-lived access JWT + rotating opaque refresh token, both in `httpOnly` cookies; passwords hashed with `bcryptjs` (cost 12). Email via `nodemailer` over SMTP.
- **Deployment target**: Vercel, two **separate projects** — `frontend/` and `backend/` each have their own `vercel.json`. There is no monorepo-level Vercel config.
- **Package manager**: npm (separate `package-lock.json` per app — no workspaces).

## Architecture Rules

- **Never add a script named `build` to `backend/package.json`.** Vercel's zero-config sees a `build` script, runs it, and then fails the deployment with `No Output Directory named "public" found` — because the backend is a serverless function, not a static site. `@vercel/node` compiles `api/index.ts` and its TypeScript imports on its own, so no build step is wanted. The equivalent local command is deliberately named **`compile`**. This exact regression broke production once; see [`TROUBLESHOOTING.md`](TROUBLESHOOTING.md).
- Keep the backend/frontend split. Do not merge them into one Vercel project unless [`DECISIONS.md`](DECISIONS.md) is updated first — this was a deliberate move (see the "Rebuild frontend in React, add real authentication, split into separate services" commit).
- The backend is already split into `config/`, `db/`, `lib/`, `middleware/`, `models/`, `routes/v1/`, `validation/` (Milestone 1, recorded in `DECISIONS.md`). Put new code in the matching folder; don't add logic back into `server.ts`, which is bootstrap-only.
- `src/app.ts` must stay the single place the app is assembled, because both the local server and the Vercel serverless entry import it. Anything that must run in production has to be wired there or into a route/middleware — **not** into `server.ts`, which never executes on the serverless path.
- New env vars go in the zod schema in `config/env.ts` and are consumed via the typed `config` object. Do not read `process.env` directly anywhere else.
- **`.env` is resolved from the backend package root, never from `process.cwd()`.** `config/env.ts` anchors the path to its own directory. Do not "simplify" it back to a bare `dotenv.config()`: that resolves relative to wherever the process was started, so a script run from `backend/scripts/` loaded **zero** variables, silently fell through to the `mongodb://localhost` default, and wrote 208 questions into the wrong database while reporting success. Use `__dirname`, not `import.meta.url` — this package compiles to CommonJS, where `import.meta` is a syntax error that would only surface on the Vercel build.
- **Any script that writes to the database must call `assertConfiguredForWrites()`** from `src/lib/envGuard.ts` as its first statement, and must be report-only unless given an explicit flag (`--write` / `--delete`). Every env var has a plausible default, which makes a misconfigured script silently successful; the guard prints the target database and refuses a local write without `--local`.
- Any new Mongoose model belongs in [`DATABASE_SCHEMA.md`](DATABASE_SCHEMA.md) before/with the code change.
- Any new route belongs in [`API_DOCUMENTATION.md`](API_DOCUMENTATION.md) before/with the code change.

## Coding Conventions

- TypeScript `strict: true` on the **backend** `tsconfig` (`backend/tsconfig.json`, along with `noUncheckedIndexedAccess: true`) — do not weaken this. The **frontend** does not currently set `strict` at all (`frontend/tsconfig.app.json`/`tsconfig.node.json` only enable `noUnusedLocals`, `noUnusedParameters`, `erasableSyntaxOnly`, `noFallthroughCasesInSwitch`) — don't assume frontend code is strict-checked; if you want frontend strict mode, that's a deliberate opt-in change to propose, not an existing rule to "not weaken."
- Frontend: functional components, hooks, one folder per page containing `<Page>.tsx` + `<Page>.module.css`. Shared visuals go in `src/components/`.
- Naming: `camelCase` for variables/functions, `PascalCase` for components/types, kebab-case is not used for filenames (existing files are PascalCase per component).
- Backend: Express route handlers are `async (req, res) => { try {...} catch { ... } }` and return the `{ success, ... }` / `{ success:false, error }` envelope via the `sendSuccess`/`sendError` helpers in `lib/apiResponse.ts`. New routes must match it so `frontend/src/api/client.ts`'s error handling keeps working. A global error handler exists as a safety net, but keep the explicit try/catch.

## TypeScript Rules

- No `any`. The `any` usages that previously existed around query building and AI-insight generation were removed in Milestone 1 — the codebase is now `any`-free in `src/`. Do not reintroduce it; add a zod schema or a model interface instead.
- Do not disable `strict` or `noUncheckedIndexedAccess` on the backend `tsconfig` to make a change compile faster — fix the actual type issue.

## Frontend Conventions

- All API calls go through `api.get`/`api.post` in `src/api/client.ts` (adds `credentials: 'include'`, JSON headers, and throws `ApiError` on non-2xx). Do not call `fetch` directly in a page/component.
- Auth state is read via `useAuth()` from `AuthContext` — never re-implement session state locally in a page.
- Route guards: `ProtectedRoute` (requires a student account) and `RequirePermission` (requires a capability) in `src/components/ProtectedRoute.tsx`. `AdminRoute` was **removed** in Milestone 3 — use `RequirePermission permission="..."`, which renders the `Unauthorized` component for a signed-in user rather than silently redirecting.
- Read permissions with `can('...')` from `useAuth()`. The permission list arrives from the backend on every auth response; **never** reimplement the role → permission mapping on the frontend, and never branch on `state.status` to decide whether something administrative is allowed (`status` says which *kind* of account is signed in, not what it may do — a promoted admin has `status: 'student'`). Wrap new authenticated pages in these rather than checking `state.status` ad hoc in the page body (existing pages do check `state.status` for conditional rendering, e.g. to show a preview vs. real data — that's fine; the *route-level* gate should still use the wrapper).

## Backend Conventions

- There are **two** auth cookies: `access_token` (short-lived JWT) and `refresh_token` (opaque, rotating). Both `httpOnly`, `secure` only in production, `sameSite: 'none'` in prod / `'lax'` in dev (prod frontend and backend are different Vercel domains, so cross-site cookies are required). Do not change these without understanding the split-domain implication — see [`SECURITY.md`](SECURITY.md).
- **Never return a raw Mongoose document from a question endpoint.** `questions.routes.ts` and `questionsAdmin.routes.ts` each build an explicit view: the student view omits `isCorrect`, `solution`, `booleanAnswer`, `numericAnswer` and `tolerance`; the author view includes them. They are two functions rather than one with an `includeAnswers` flag on purpose — before Milestone 4 this endpoint was unauthenticated and served the whole answer key. Do not merge them.
- Author-written content that may contain maths must be validated with `validateMathContent()` from `lib/mathContent.ts`, and rendered only through `frontend/src/components/MathText.tsx`. Never put question content into `dangerouslySetInnerHTML` yourself — the safety of the whole scheme is that prose becomes a React text node and only KaTeX output becomes HTML.
- **The answer key must never reach the client before it should be revealed.** Two functions reveal a correct answer and no more may be added: `sessionReviewView()` in `services/practiceService.ts`, which throws unless the session is `submitted`, and `attemptReviewView()` in `services/mockTestService.ts`, which throws unless the attempt is submitted **and** the mock test's own `reviewPolicy` currently permits it. Every in-progress view composes the shared answer-stripped `services/questionView.ts`. If you add a surface that serves questions, reuse `studentQuestionView`; do not hand-write a projection, because a forgotten field is an answer leak. Grading is server-side, always: the browser is never given the means to mark its own work.
- **A mock test decides when a score and when an answer key may be shown**, through `resultDisplay` and `reviewPolicy`. `disclosureFor()` in `services/mockTestService.ts` is the only place either is interpreted — do not branch on them anywhere else, and do not snapshot them onto an attempt (an administrator has to be able to release results after the window closes).
- **Practice sessions and mock-test attempts snapshot the answer key at serve time.** Grading reads that snapshot, not the live `Question`, so editing or re-pricing a question cannot retroactively change a paper somebody has already sat. Do not "simplify" grading to re-read the question.
- **There is exactly one grader: `services/grading.ts`.** `isAnswered`, `gradeEntry` and `gradeEntries` are shared by practice, mock tests and the daily challenge, over the one served-question shape in `models/attemptAnswer.ts`. Do not write a second marking function for a new surface — two graders eventually disagree, and a grader that disagrees with the answer key is a wrong score on a student's report.
- **For a timed surface, the server owns the clock.** `MockTestAttempt.expiresAt` is computed and stored when the attempt is created and never recomputed. No request body may carry a time, an elapsed duration or a deadline; an answer arriving after the deadline is refused and **not stored**, and a late submission is graded as at the deadline. A countdown in the browser is a display derived from `secondsRemaining` — never an input.
- **A submission that must happen once is closed by a conditional write**, not a read-then-write check: `finalizeAttempt()` updates with `status: 'in_progress'` in the filter and reports whether that write won, which is what gates the XP award. On a serverless platform a check and its write can land in different invocations.
- **There is exactly one reward engine: `services/rewardService.ts`.** Call `grantReward()` — never `recordActivity()` directly (only the engine and `scripts/backfill-activity.ts` may), and never compute an XP amount in a route. A caller supplies *facts* about what happened (`context: { answeredCount }`); the engine decides eligibility and price. Adding a reward to a new surface means one call, not a new rule.
- **Never query a database from `lib/achievements.ts`, `lib/badges.ts` or `lib/journey.ts`.** All three are pure functions of `RewardFacts` (`lib/rewardFacts.ts`), assembled once by `buildRewardFacts()`. To award for something new, add a fact there and supply it in the engine — that two-step friction is deliberate, and it is what has kept unearnable rows off the dashboard.
- **XP amounts are administrator-tunable; the rules are not.** `RewardSettings` overrides amounts only. Cardinality (`ONCE_PER_DAY`), eligibility and the level thresholds stay in code. Re-pricing must never affect history: `StudentActivity.xpAwarded` is a snapshot, and a total is the sum of those recorded values — do not "optimise" that into a lookup against the current table.
- **There is exactly one ranking service: `services/leaderboardService.ts`.** Every standing the product shows goes through it — the landing page, the dashboard's rank tile, the `/leaderboard` page and the Hall of Fame's XP board — so a rank cannot disagree with itself on two screens. Do not write a second aggregation that orders students; add a scope or a period to the one pipeline. Three rules travel with it: **nothing is stored** (there is no `Leaderboard` collection; a board is a `$sum` over `StudentActivity`, so it cannot drift from the XP it ranks); **equal XP shares a rank**, with the listing order fixed by a *total* order (XP → who reached it first → account id, the last key being what makes pagination safe); and **no request may supply a ranked value** — XP, score and rank are absent from the query schema rather than filtered by the handler. The frontend renders rows in the order it receives them and never re-sorts.
- **`attachUserIfPresent` is not a gate.** It attaches session claims when a cookie is present and never rejects, and exists so one public endpoint (the leaderboard) can differ in *content* for a signed-in caller. Anything decided on it is a presentation decision; a capability decision still goes through `requirePermission`, which rejects and re-reads the role from the database. Do not reach for it to make a route "optionally authenticated" when what you mean is authorised.
- **A public list must stay a list, not a roll.** The leaderboard publishes children's names (masked to a first name and last initial by `displayNameFor()`, the only function allowed to decide that) and caps an anonymous caller at the top 100. If you add pagination or a new public board, re-check that cap — Milestone 5's page-size limit stopped protecting anything the moment pages arrived, and the property had to be restored deliberately. See [`SECURITY.md`](SECURITY.md).
- **There is exactly one payment path: `services/paymentService.ts`**, and exactly one paywall: `middleware/requireEntry.ts`. Three rules travel with them. **The browser is never believed about money** — `POST /payments/orders` takes no body at all (the amount comes from `PaymentSettings`, the student from the token), and both paths that mark a payment captured verify an HMAC signature in constant time; a signature proves a payment is *genuine*, not that it is *yours*, so ownership is checked separately. **The entitlement is derived, never stored** — it is "has a captured `Payment` with purpose `olympiad_entry`", and there must be no `hasPaid` flag on `Student`, for the reason XP and the leaderboard are derived: a stored boolean is a second source of truth about money. **Capture is idempotent by conditional write**, because the return journey and the reconcile/webhook path routinely arrive in the same second and on serverless land in different invocations.
- **The entry fee gates the official Olympiad and nothing else** (owner decision, 2026-08-17). Practice, mock tests, the daily challenge and analytics are **free** — a student prepares for free and pays only to compete. It briefly gated all four on 2026-08-16 and was reversed the next day; do not re-widen it without the owner. Tests assert the free surfaces are *not* gated, so a quiet widening fails the suite.
- **The paywall is mounted, never called.** Add `requireEntry` to a gated route; do not call `hasEntryEntitlement()` from a handler. A surface that has to remember to ask will eventually forget, and a forgotten paywall looks exactly like a working one until somebody notices the revenue. It answers **402, not 403** — the frontend branches on that to show a pay button instead of the `Unauthorized` dead end — and it must be mounted **after** the auth gate and `ensureDb` and **before** the handler, so an absent id returns 402 rather than 404. The exam's check originally sat inside its service, after the 404, which let an unpaid caller probe which exams existed; there is a regression test.
- **Payment is not a permission.** Do not add `entry:paid` to `src/lib/permissions.ts`. That table answers "what may this *role* do?" and its value is that it can be checked by reading it; payment is a fact about a collection, and two students with the same role differ by it. **Staff are not exempt** either — a promoted admin is an ordinary student account, and a role exemption inside a payment gate is how people get silently admitted.
- **`requirePermission('...')` is the gate for new routes**, not a role check. The role → permission table in `src/lib/permissions.ts` is the *only* place a role may be mapped to a capability — **never** compare `req.user.role` to a literal in a handler or route (see [`DECISIONS.md`](DECISIONS.md)). Add a permission to that table if none fits. `requireAuth(...roles)` still exists but only for gates that genuinely concern identity rather than capability (e.g. `/auth/logout-all`). For a decision that depends on the data being addressed rather than the path, use `callerCan()` / `callerCanFresh()` — the latter re-reads the role from the database and is what you want before granting access to *someone else's* data.
- Authentication is stateless (no DB read). **Authorization is not, for privileged permissions**: `requirePermission` re-reads `role`/`status`/`tokenVersion` from MongoDB so a demotion or suspension takes effect at once instead of surviving the access token's TTL. Do not "optimise" that read away. It also means privileged routes need a database connection in order to authorize, and answer 503 without one.
- Any route that changes an account, a role, or the question bank must call `recordAudit(req, {...})` from `src/lib/audit.ts` with an action from `src/models/AuditLog.ts`. Audit writes are best-effort by design and must never fail the action they describe.
- Never store a token in the database in plaintext. Use `hashToken()` from `lib/tokens.ts` (SHA-256) for refresh and email tokens; use `lib/password.ts` (bcrypt) for passwords. Never log a raw token outside the dev email transport.
- Auth responses must not reveal whether an account exists. Login uses one message for unknown-account and wrong-password; `forgot-password` and `resend-verification` always return the same generic 200.
- Every route returns JSON with a `success` boolean. Never return a bare array/object without it.

## Database Conventions

- **The official exam is REAL as of Milestone 13**, and so are certificates. `Exam`, a rewritten `ExamAttempt` and a rewritten `Result` are all written by routes now. The Milestone 12 note that said never to build over them is superseded — but the *reason* it existed still governs: nothing may show a figure the database cannot be asked for. Milestone 12 deliberately shipped **twelve of fourteen** requested admin areas for this reason: there is no results console and no certificate management, because both would be permanently empty and would recreate the fabricated-data problem Milestone 5 spent a follow-up pass deleting. Real scored data lives in `MockTestAttempt`. See the Milestone 12 ADR.
- **There is exactly one student analytics derivation: `services/analyticsService.ts`**, and it is **derived on read with no collection behind it** — the same decision XP, levels, streaks and the leaderboard rest on. Do not add a `StudentAnalytics`-style cache; the previous one was deleted in Milestone 15 after ten milestones of never being written. Three rules travel with it: **raw counts are summed and percentages derived last** (combining 1/1 and 1/9 must give 20%, not the 55% an average of percentages gives — there is a test); **`null` is not `0`**, because "answered nothing" and "answered, all wrong" are different facts about a child; and **a strength or weakness needs `MIN_AREA_SAMPLE` answers**, because one wrong answer is a real 0% and a fabricated diagnosis.
- **A question becomes practice content by being PUBLISHED, and there is no `PracticeSet`.** Practice is student-initiated — `startPracticeSession()` `$sample`s published questions for the class, chapter and difficulty the *student* chose — so there is nothing for an administrator to assign to. "Assign to practice" is `PATCH /admin/questions/bulk-status`, and the preview beside it calls the student picker's own `getPracticeAvailability()` so it cannot disagree with what it previews. Do **not** add a curated practice collection without an ADR: it would be a second path serving questions to students, and every such path has to re-implement the answer-key snapshot rules. See the Milestone 21 Phase G ADR.
- **`changeQuestionStatusBulk()` loops; it must never become an `updateMany`.** A bulk write would skip `assertPublishable()` — the check that refuses a question with no solution or no resolvable answer key — and so would publish ungradeable questions to children in batches. A partial success is the normal outcome and answers **200 with per-question results**, never a 400, and nothing is rolled back. There is a test that publishes two questions where one lacks a solution.
- **A literal admin path that looks like an id must be declared before `/:id`.** Express matches in declaration order, so `GET /admin/questions/practice-availability` placed after `GET /admin/questions/:id` is swallowed and answered 400 — which happened, and now has a regression test. Same trap as mounting `questionsImport` ahead of `questionsAdmin`; check the ordering whenever you add a non-parameter route to a router that has a `/:id`.
- **There is exactly one path to a recommendation: `services/recommendationService.ts`**, and like analytics it is **derived on read with no collection behind it**. Four rules travel with it. **An engine may not query a database** — it is a pure function of `RecommendationFacts` (`lib/recommendationTypes.ts`), assembled once by the service, exactly as the reward catalogues are pure functions of `RewardFacts`; add a fact there and supply it in the service. **An engine does not describe itself** — `recommend()` returns a `RecommendationDraft` (content only) and the service stamps `engine`, `generatedAt` and `hasData`, so nothing can claim to be a model or claim data a student lacks; do not add those fields to the draft type. **Every recommendation carries a required `basis`** naming the counts it came from — a recommendation that cannot state its evidence must not be constructible, which is the type-level form of the rule that deleted `generateAIInsights()`. And **nothing may recommend what the bank cannot serve**: a practice suggestion is joined against `getPracticeAvailability()` for the student's own class, because a link to a topic with no published questions lands a child on an empty picker.
- **Generated questions are NEVER saved without human approval** (Milestone 18). `proposeQuestions()` returns candidates and writes no `Question`; `approveQuestions()` is the only writer and **re-validates from scratch**, because what it receives is whatever the review screen sent after the examiner edited it. Do not "optimise" that second validation away, and do not add a staging collection — candidates live in the browser on purpose, so the bank cannot fill with machine output nobody read. There is **no template/placeholder generator any more**: an unconfigured key is a 503 naming the variable, a failed provider is a 502 carrying its own words, and neither invents filler. **Rejection has no route that deletes anything** — nothing was stored, so `POST .../reject` only counts what the examiner discarded against the generation log, and that count is the one honest measure of whether a prompt configuration works.
- **Generation is the only route in the product whose every call spends third-party quota**, so `generationLimiter` is mounted on it **ahead of the permission check**, and `GENERATION_MAX_QUESTIONS` / `GENERATION_MAX_INSTRUCTION_CHARS` bound a single request in the zod schema. Do not put the limiter on the status or model-list routes (one makes no network call, the other is cheap metadata whose failure costs only the model picker), and do not raise the *hard* ceiling of 20 questions per batch in code — the environment variable may lower how many are asked for, but a batch has to stay reviewable by one human in one sitting, which is a product rule rather than a cost one.
- **The examiner's extra instructions are untrusted input.** They go last in the prompt, fenced, introduced as a *preference* that cannot override the class, chapters, subtopic, type, count, language, marks, formatting rules or output shape — and the fence delimiter is **stripped out of their text** so it cannot close the quotation early and continue as though it were the system talking. Keep that ordering: every constraint that matters must be stated before any user-controlled text is reached. The real defence is still that nothing the model returns is trusted.
- **`fill_blank` is auto-graded against author-listed `acceptedAnswers`** via `normalizeAnswerText()` in `services/grading.ts`, which forgives capitalisation, whitespace and a trailing full stop and **nothing else**. Do not add fuzzy matching or synonyms — a grader that guesses can silently mark a wrong answer right. **Do not add a short-answer type**: it cannot be auto-graded without either a human marking queue or sending a child's writing to a model, and both were rejected (see the Milestone 18 ADR). Note the trailing-stop rule strips only a *sentence-final* stop; an internal one is a decimal point and must survive.
- **Adding a question type touches far more than the model**: validation, `services/grading.ts`, `models/attemptAnswer.ts`, **three** snapshot builders (`attemptSnapshot.ts`, `practiceService.ts`, `dailyChallengeService.ts` — they are not consolidated yet), four answer-application paths, every review view, and five frontend runners. Keep new answer-key fields **non-optional** on `AttemptAnswerEntry` so the compiler finds every site; an optional one was missed in two of three builders during Milestone 18 and would have produced wrong marks.
- **There is exactly one AI integration: question drafting** (`services/geminiQuestionGenerator.ts`, Milestone 17; rebuilt on the official `@google/genai` SDK in Milestone 20), and it sits behind the seam in `lib/questionGeneratorTypes.ts`. Four rules travel with it, all enforced in `services/questionGeneratorService.ts` so a second caller cannot skip them. **The taxonomy comes from the request, never the generator** — `GeneratedCandidate` has no subject/topic/class/difficulty field, and do not add one. **Every candidate passes `createQuestionSchema`**, the same schema and the same `validateMathContent()` a hand-authored question passes; never write a model-specific validator, because the model-facing one would be the weaker of two. **A bad candidate is rejected and reported, never repaired** — a plausible-looking repaired answer key is worse than a missing question. **With no `GEMINI_API_KEY` nothing is generated at all**: the endpoint answers 503 naming the variable. There is no template fallback (deleted in Milestone 18) and nothing may be invented in its place — but the rest of the product must stay complete with no AI credential, so never make another feature depend on one.
- **Retries for the model are ours, not the SDK's, and they share one deadline.** `attemptGenerate()` retries only what is genuinely transient — 429, 5xx, a timeout — up to `GEMINI_MAX_RETRIES`. A rejected key, a blocked prompt and a retired model name are never retried, because repeating them spends quota to receive the same refusal. All attempts share **one** time budget: a signal built outside the loop leaves a retry aborting instantly (which reported "timed out" for a real 503 — there is a `TROUBLESHOOTING.md` entry), and a fresh full-length signal per attempt outlives a serverless invocation. If you add a retry around any other request timeout, that trap is waiting.
- **Structured output is one schema per question type**, built by `responseSchemaFor()`. A numeric request's schema has no `options` property, so options cannot come back to be rejected; `minItems`/`maxItems` pin the batch and option counts. `marks` and `negativeMarks` are deliberately **absent** — the paper is priced by the examiner, and the model has no opinion worth reading. Adding a question type means a sixth schema variant as well as everything in the list further down.
- **`lib/questionQuality.ts` annotates; it never rejects.** It is a pure function of the candidates, like the reward catalogues, producing advisory findings a reviewer sees beside each question. **It does not verify that a question is mathematically correct, and nothing may imply that it does** — the first live generation run of the new code returned a well-formatted question with a *wrong* answer key, which is why the review step is mandatory and why this module's claims stay narrow. The rules that are always defects live in `createQuestionSchema` and reject there. Do not promote a warning into a rejection: a rule that is sometimes wrong must not throw a question away.
- **There is exactly one path from a file to the bank: `services/questionImportService.ts`** (Milestone 21), and it is the AI generator's shape on purpose. **Uploading writes nothing; `approveImport()` is the only writer, and it re-validates from scratch** — what comes back is whatever the review screen sent after the examiner corrected it. There is **no staging collection**: candidates live in the browser, so the bank cannot fill with machine-read text nobody looked at. Questions are created as **`draft`** — importing is not publishing — and `publish: true` is honoured only through `changeQuestionStatus()`, so an import cannot route around "a published question must be explainable to a student".
- **There is still exactly one screener.** `screenEach()` in `services/questionGeneratorService.ts` is it, and `screenCandidates()` delegates to it. Imports needed a target **per candidate** (a spreadsheet files row 3 and row 40 under different chapters), which is why it was generalised rather than copied — two screeners would eventually disagree about what may become a question, and the more permissive one would decide. Do not write a second one for a new format, and remember that changing `screenEach()` changes the gate for the generator too.
- **One canonical candidate, and no `ExcelQuestion`.** `ImportedCandidate` (`lib/importTypes.ts`) composes `GeneratedCandidate` **verbatim** for its content half. A spreadsheet row, a Word paragraph, an OCR'd photograph and a model's draft all become the same thing before anything decides whether to keep them. A type per format would mean a validator per format, and the weakest one would decide what got in.
- **An importer suggests a taxonomy by NAME; it never supplies an id and never creates one.** `ImportedTaxonomyHint` carries the class/chapter/subtopic/difficulty *as the file wrote them*, and the service resolves them against the live taxonomy. The asymmetry is load-bearing: a row that is **silent** takes the examiner's default, and a row that says something **unresolvable is refused with its row number**. Silently defaulting `Class 13` would file a question under the wrong cohort and serve it to the wrong children. Name matching forgives case, spacing and `8` / `8th` / `Grade 8`, and nothing more — `Clss 8` is refused, on the same principle as `normalizeAnswerText()`. **One bad spreadsheet must never be able to reshape the syllabus.**
- **Import provenance is read back from `ImportBatch`, never from the request body.** `source` is the one field worth lying about: a client that could set it could file questions a model read off a photograph as hand-written ones. The browser supplies only the `batchId` we issued, and a batch that names no row is a **400** rather than a degraded stamp, because that row is also where the subject comes from. Keep `source` and `generatorKind` as **separate** facts — an image import is `image_import` *and* `generatorKind: model` with a model name; an Excel import is `excel_import` with `deterministic` and no model.
- **Nothing in the importer touches the filesystem.** Uploads arrive as base64 data URLs in the JSON body, like the registration photo, and are parsed from a `Buffer`. That is why temp-file cleanup, safe filenames and path traversal are *absent* risks here rather than mitigated ones — do not "improve" this into a multipart parser writing to `/tmp`. A filename is a **label** for error reports, never a path. The one thing genuinely not defended against is a **decompression bomb**; see `SECURITY.md`.
- **An import parser is a shape adapter, not a gate.** `services/excelImportParser.ts` turns a row into an `ImportedCandidate` and does **not** judge the question — `createQuestionSchema` does, through the shared screener. Keep the three-way split that makes the messages useful: a row that **cannot become a candidate** is a `ParseFailure` naming its row number; a row that becomes a **bad candidate** is left to the screener, so the examiner reads the same words a hand-authoring one would; a row we had to **interpret** carries a `note`, which never blocks anything. Do not move a screener rule into a parser, and do not let a parser "fix" a row.
- **Reading an answer is shared by every format: `lib/importAnswerText.ts`.** Option letters, `TRUE`/`FALSE`, accepted answers, type names and type inference all live there, pure and I/O-free. "The answer is B" must mean the same thing in a spreadsheet cell and on an `Answer: B` line — two readers would drift, and the same question imported twice would carry two different answer keys. Adding a format should need **no new answer reading**. Two decisions in there are easy to get subtly wrong: the inference order (options → true/false → number, because `1` is a boolean spelling) and the `|` separator.
- **There is exactly one Gemini call: `requestGeminiJson()`** in `services/geminiQuestionGenerator.ts`. Question drafting and image transcription both go through it. What it owns is the set of things already got wrong once: the client via `clientFactory` (the test seam — so no test can reach the network), the credential check, `attemptGenerate()` and its **single shared deadline**, `describeFailure()`, `redact()`, and the blocked-prompt and `MAX_TOKENS` cases. The prompt, the schema, the temperature and the truncation remedy are parameters. Do not add a second call site.
- **For image import the model transcribes; it does not answer.** The response schema asks for what is *printed* — `questionText`, `options`, and `answer` **as written** — and deliberately has **no** `isCorrect`, `booleanAnswer`, `numericAnswer` or `marks`. Those are derived by `lib/importAnswerText.ts`, so "the answer is B" means the same thing as it does in a spreadsheet. Do not add typed answer fields to that schema: it would make a model the authority on what counts as correct. **A question with no printed answer is refused, never given one** — a calculated answer is indistinguishable from a printed one, and children would be marked against it.
- **Never read marks, class or topic off a photograph.** They come from the upload defaults only. A misread "(4 marks)" changes a score and a misread page header files a question for the wrong cohort — the same rule that makes an unresolvable spreadsheet `Class` a reported error rather than a default.
- **Every image import carries `OCR_STANDING_WARNING`, and it is not boilerplate.** OCR of mathematical notation fails quietly — a dropped exponent, a minus read as a hyphen — producing a question that reads plausibly and is wrong. The mandatory review is the only control, and a reviewer who has not been told will skim. Nothing may imply a transcription is verified.
- **DOCX extraction is deliberately AI-free, and the image path is deliberately not.** A `.docx` is text we already have, so a model would add cost, latency, a third party on every import, and a credential dependency in a *core* format — see the Milestone 21 ADR. What absorbs the reduced capability is honesty: **it never guesses quietly.** Every interpretation is a `note`, every unusable block is a failure naming its question number, and a document that yields nothing says what was looked for rather than returning one enormous candidate. Do not add a model here to "improve accuracy".
- **Two Word failure modes look like success, and both must keep their warnings.** Word's **automatic numbering** does not survive text extraction (the digits are in `numbering.xml`), so a document numbered by the toolbar would merge into one question — there is an `Answer:`-terminated fallback, and it announces itself because it is the case most likely to split a question wrongly. And **Word equation objects are dropped silently by `mammoth`**, so an affected question imports looking complete with its formula missing mid-sentence; `containsWordEquations()` warns and names the fix. Do not "simplify" either warning away, and do not start parsing `numbering.xml` — that is a rabbit hole, and the warning solves the real problem.
- **Be tolerant of the file and strict about the data.** Column order, heading capitalisation and punctuation, extra columns, a title row above the header, and multiple sheets are all accommodated, because an examiner exports from whatever they already have. The *data* is not: a `Class` of `13`, a chapter that does not exist, or a `Marks` cell containing a word is reported **with its row number** rather than defaulted. Silently defaulting a class serves a question to the wrong children, and silently defaulting marks changes a score.
- **`fill_blank` accepted answers in a spreadsheet are separated by `|`, never `,`** — `1,000` is one answer containing a comma. A comma-separated list would split real answers into wrong ones, and the failure is invisible until a correct answer is marked wrong. If you add a list-valued column, pick a separator that cannot occur in the values.
- **The Excel template is generated per request** (`buildExcelTemplate()`), never checked in, because its `Class`/`Type`/`Difficulty` dropdowns come from `CLASS_LEVELS`, `QUESTION_TYPES` and `DIFFICULTIES`. A static file would advertise a value the API refuses as soon as one of those changes. Its example rows deliberately leave `Topic` **blank**: naming a chapter that exists only in this project's seed data made every examiner's first import open with five rejected rows. There is a test asserting the template imports cleanly through our own parser — keep it, it has caught two defects already.
- **A header row needs two matching columns, not one.** `HEADER_COMPANIONS` exists because a one-match rule read the template's own *Instructions* glossary — whose first cell is the word `Question` — as a header and imported twelve rows of prose as questions. Any workbook with a legend or a column-guide sheet has that shape.
- **`importLimiter` is mounted ahead of the permission check** on the upload routes, exactly as `generationLimiter` is: an upload decompresses an archive and validates hundreds of rows, and the image path spends provider quota **per file**, so ten photographs is ten model calls. Do not put it on the status, approve or reject routes. `IMPORT_MAX_QUESTIONS` may lower how many one import offers, but do not raise `IMPORT_HARD_MAX` (500) in code — a review step nobody can finish is not a review step.
- **`POST /admin/questions/import/validate` must call the same screening function approval calls** (`screenEach()`), exactly as the generator's dry run must. Its whole value is that its answer *is* the answer approval will give; a check that passes where the save would fail is worse than no check, and there is a test that sends one batch to both endpoints and compares the reasons string-for-string. It writes **nothing** — not even an `ImportBatch` counter — which is why it is not rate limited and takes no `batchId`.
- **`verdicts` from a dry run are positional over what was sent.** A client must key them to its own rows *at send time*: indexing by a question's current position in a selection is wrong the moment the reviewer ticks anything, and would show one question's rejection reason against a different question. The import review page holds them in a `Map` by `clientId` for this reason.
- **Saving and publishing are two outcomes on the approve route**, and a client that conflates them lies to the examiner. It returns `{ questions, rejected, published, publishFailures }` and **no `created` count** — a question with no solution saves as a draft and is *refused* publication. Assuming `created` is how the review page came to render "Saved undefined questions"; see `TROUBLESHOOTING.md`.
- **With no frontend test suite, a browser pass is not optional for a new admin page.** The two Phase F defects — an assumed `created` field and ignored `publishFailures` — were both assumptions the *client* made about a response shape, and neither was reachable from 1,086 backend tests. Read the route's `sendSuccess(...)` call rather than inferring the shape from the service behind it.
- **`POST /admin/generate-questions/validate` must call the same screening function approval calls** (`screenCandidates()`). Its whole value is that its answer *is* the answer approval will give; a check that passes where the save would fail is worse than no check. It writes nothing, not even a log row, which is why it is not rate limited — an examiner should be able to check their edits freely.
- **`Question.provenance` is written only by `approveQuestions()`, and its generator facts are read back from our own `GenerationLog` row** using the `logId` we issued — never from the request body. `source` is the field worth lying about: a client that could set it could file machine-written questions as hand-written ones. It is a parameter of `createQuestion()` rather than part of `QuestionContentInput` because content is what a reviewer may edit and provenance is not. Do **not** add a second review lifecycle (`PENDING_REVIEW` and friends): `status` already is the editorial workflow, and "rejected" has no row to live on because nothing is stored until approval.
- **No student data may be sent to any model.** The question-drafting payload is a subject name, a topic name, a class level, a difficulty and the examiner's own instruction — there is a test asserting the request body contains no student fields. Adding a second AI call means answering the children's-privacy question again, from scratch, with the owner.
- **Do not label anything AI unless a model really produced it.** `EngineDescriptor.kind` (recommendations) and `GeneratorDescriptor.kind` (question drafting) are `'statistical'`/`'template'` versus `'model'`, and both are statements of fact the UI prints and the audit trail records. Recommendations use **no AI** and adding one there is a cost *and* a children's-privacy decision for the owner — see the three Milestone 16 ADRs, and the Milestone 17 ADR for why question drafting is a genuinely different case rather than a reversal. Statistical findings are asserted on a **95% Wilson interval** (weakness on the upper bound, strength on the lower) over the shared `MIN_AREA_SAMPLE` floor, so a perfect five is not a strength and five wrong answers are not a weakness; both are pinned by tests.
- **Grading reads the answer-key snapshot; analytics joins the LIVE taxonomy.** Both are deliberate and they are opposites. A mark is a historical fact about one paper, so `services/grading.ts` never reads the live `Question`. "How am I doing in Trigonometry?" is a question about the taxonomy as it stands now, so the analytics aggregations `$lookup` the current `topic`/`subject`/`difficulty`. Do not "fix" either to match the other — see the Milestone 15 ADR.
- **`answeredAt` is the stored materialisation of `isAnswered()`.** Every write path sets it as `isAnswered(entry) ? now : null`, including on a cleared answer. Aggregations read it rather than re-deriving the per-type rule in aggregation expressions, which would be a second grader by another name. Note also that `isCorrect` is **three-valued** on a stored entry — `true`, `false`, or **`null` for unanswered** (written by `gradeEntries()`) — so correctness must be counted as an explicit `true`; `$ne: false` counts every blank as correct.
- **Every figure on an admin page must be counted from a collection.** `services/platformAnalyticsService.ts` is the one place platform-wide figures are assembled, and it has no estimates, projections or "engagement scores". Where there is no data it returns `0`, or `null` for an average — "nothing has been sat" and "everybody scored zero" are different facts. If a number cannot be queried, report `null` and let the UI say so (the rewards overview does exactly this for streak achievements, which an aggregation cannot answer).
- **`shiftDay(key, n)` returns the key `n` days BEFORE `key`.** A negative value moves *forward*. Getting that backwards produced a future cut-off that matched nothing, so two analytics windows silently read zero however busy the platform was. There is a regression test.
- **A notification is one document with an audience rule** (`services/notificationService.ts`), never fanned out per recipient, and `inboxFilter()` is the single definition of what a student can see — shared by the inbox, the unread count and `isVisibleTo()` so the bell cannot disagree with the list. **Never hand-write the audience comparison**: the mark-as-read route did, and it was correct for two audiences and would have silently refused every per-student notification Milestone 14 added.
- **`Notification.audience: 'student'` is system-only.** It is absent from the staff composer's schemas (`STAFF_AUDIENCES`), not filtered out in a handler. A per-student notice carries a score, a rank and a certificate tier, so leaking one across the class boundary is a disclosure bug, not a display bug. Do not add a staff path to it.
- **There is exactly one email queue: `services/emailOutbox.ts`.** Call `enqueueEmail()` — **never** `deliverEmail()`, which only the drain may call. **No user-facing request may await SMTP.** Before Milestone 14, registration awaited it inline and swallowed the failure, which destroyed the verification link a student needs in order to log in at all; it also made `forgot-password` a *timing* oracle for account existence, defeating its deliberately identical message. A row is claimed by a conditional write that pushes `nextAttemptAt` forward (a visibility timeout) — do **not** add a `sending` status, because a frozen serverless container would leave a row stuck in it for ever.
- **There is exactly one path for an automated notification: `postSystemNotification()`.** Callers supply facts (the event, the copy, who it is for); the engine decides email eligibility, preference and dedupe — the same division of labour as `grantReward()`. Add an event to `lib/systemNotifications.ts` (pure data, no database, like the achievement catalogue) and one call at the place the event really happens. Wire it through `services/systemNotifier.ts`, so exam and account code stays free of notification copy.
- **Any system notification an administrator can trigger twice needs a `dedupeKey`.** Releasing an exam's results is idempotent by design, and the partial-unique index on `Notification.dedupeKey` is what stops a second click telling the whole cohort again. An index, not a check — two concurrent invocations would both pass a check.
- **`security` and `transactional` email are not preferences.** `isOptionalCategory()` says so, and `emailAllowedFor()` is the only place a preference is interpreted. Its rule order is load-bearing: the category check runs **before** the account-status check, because a *suspension notice* is the one message a suspended account must still receive. Do not add a switch for either — "you may turn off the warning that your password was changed" only ever helps an attacker.
- **A preference suppresses email, never an in-app row.** Everything is always written to `Notification`. Suppressing at write time would make "unread" and "never delivered" indistinguishable, and a notice board a student can empty is not a record.
- **The entry fee is administrator-editable, and it gates the platform.** `PaymentSettings` is a single pinned document (`key: 'default'`, unique index), like `RewardSettings` — the fee is **business configuration, not a credential**, so it must never move into an environment variable: that would make changing the price a redeploy, put it out of reach of the person who decides it, and leave no record of who changed it. Only the Razorpay credentials are env vars. `entryFeeEnabled` **defaults to `true`** — a paywall nobody remembered to switch on is not a paywall — but the switch must stay, because it is the only answer to a provider outage during an exam window and to running a cohort free; and it must stay **explicit** rather than inferred from the credentials being absent, because "we chose to run this free" and "the keys are missing" must never look the same. `Payment.amount` is a snapshot: re-pricing must never touch a captured payment, the same rule `StudentActivity.xpAwarded` follows.
- MongoDB via Mongoose, one model per file in `src/models/` — **27 models** (Milestone 21 added `ImportBatch`, the record of one bulk question import, and extended `QUESTION_SOURCES` with three `*_import` values; Milestone 20 added none: it extended `Question` with an embedded `provenance` subdocument and `GenerationLog` with `rejectedByReviewer`; Milestone 19 added `Payment` and `PaymentSettings`; Milestone 18 added `GenerationLog`) (`Notification.ts` registers both `Notification` and `NotificationRead`; see [`DATABASE_SCHEMA.md`](DATABASE_SCHEMA.md)), plus `attemptAnswer.ts`, which is a *shared subdocument* embedded by `PracticeSession`, `MockTestAttempt` and `DailyChallengeAttempt` rather than a model. `AuditLog`, `StudentActivity`, `PracticeSession`, `MockTestAttempt`, `DailyChallenge` and `DailyChallengeAttempt` deliberately have **no** TTL index, unlike the two token collections — expiring a row would take XP or a practice history away from a student who earned it. `ExamAttempt` and `Result` **are written**, by the official exam built in Milestone 13 — an earlier revision of this line said they were not, which stopped being true then. Do not reuse them for practice: practice has its own `PracticeSession` collection on purpose (see [`DECISIONS.md`](DECISIONS.md)). **`StudentAnalytics` was deleted in Milestone 15** — it was the last model read by the product and written by nothing, and analytics are now derived on read. Every remaining model is both read and written; if you add one that is not, say so explicitly and give the reason.
- **`Question` was rewritten in Milestone 4** and cannot read documents created before it (`subject` went from `String` to `ObjectId`, which throws a cast error on read rather than being a tolerable missing field). Legacy documents must be deleted with `backend/scripts/migrate-questions.ts` — see [`TROUBLESHOOTING.md`](TROUBLESHOOTING.md).
- **A day's challenge is pinned, never recomputed.** `resolveChallengeFor()` returns the stored `DailyChallenge` for a `{day, classLevel}` and only computes one when none exists, writing it before serving it. Do not reintroduce a picker that derives today's question from the current bank on each read: `hash(day) % publishedCount` changed which question "today" was whenever anything was published, and made a past day unrecoverable.
- **Mock tests are their own two collections** (`MockTest`, `MockTestAttempt`) and are not practice, and not the official exam. Do not write mock attempts into `ExamAttempt`, and do not point the dashboard's official test panel at them — a mock is a rehearsal, and conflating the two is what the separation exists to prevent (see [`DECISIONS.md`](DECISIONS.md)).
- Topics **and subtopics** are the same `Topic` collection, distinguished by a nullable `parent` and a derived `depth` capped at 1. Do not add a separate `Subtopic` model without a `DECISIONS.md` entry.
- `backend/.env` holds the **production** Atlas URI, so `npm start` locally writes to live data. Use `npm run dev:local --prefix backend` for local work — it forces a localhost database, and since Milestone 7 also points SMTP at a dead port and turns off email verification, so a local registration cannot email a real person. Do not remove either override; `.env` holds working SMTP credentials and `dotenv` will not overwrite an already-set variable, which is what made a local test registration mail a stranger.
- `Student.passwordHash` is `select: false`. A query that needs it must opt in with `.select('+passwordHash')`; never remove that guard.
- `Student.email` is required and unique, and was added in Milestone 2, so **documents created before it lack the field** and will fail validation on save. There is no migration script — see [`TROUBLESHOOTING.md`](TROUBLESHOOTING.md).
- Any route that touches the database must have the `ensureDb` middleware applied **after** validation/auth. Without it the route will work locally but fail in production, because the serverless entry never runs the local bootstrap that connects at startup.
- Student lookups use Mongo's own `_id` for the token `sub`; the human-facing identifier is `studentId`, which has **two namespaces**: `AMIT_0000`–`AMIT_9999` for entrants and `ADMIN_0000`–`ADMIN_9999` for the bootstrap staff account. `AMIT_xxxx` is the competitor numbering — the number a child writes on an exam paper — and there are only ten thousand of them, so staff must never be given one. It is now **uniquely indexed**, with registration retrying on collision, so it is safe to rely on — but it is still a plain string, not an `ObjectId` reference.

## API Conventions

- REST-ish, prefixed **`/api/v1/...`** (canonical). The unversioned `/api/...` is a compatibility alias mounting the same router — add new routes to `routes/v1/` only, never to the alias separately. Remember the alias when reasoning about access control: a gate must hold on both prefixes (a test asserts it does).
- Non-public routes call `requirePermission('...')`. Use `requireAuth(...)` only for an identity-based gate.
- Daily-challenge scheduling is gated on `challenges:write`; answering one is an identity gate (`requireAuth()`), like the rest of `/me`.
- Mock-test authoring is gated on `mocktests:write`; sitting a test is gated on the student-level `exam:take`. Student attempt routes never accept a student id — the account comes from the token's `sub`, and ownership is part of every query.
- See [`API_DOCUMENTATION.md`](API_DOCUMENTATION.md) for the authoritative, currently-implemented list. Several routes exist on the backend but are **not called by the frontend at all** (`/api/daily-challenge`, `/api/leaderboard`, `/api/certificates/:studentId`) — don't assume a page is wired up just because a matching endpoint exists.

## Authentication Conventions

- **Three roles**: `student`, `admin`, `superadmin`. **Every one of them is a `Student` document** since Milestone 11 — including the root `superadmin`, which is auto-provisioned from `ADMIN_EMAIL`/`ADMIN_PASSWORD_HASH` the first time anyone signs in at `/api/v1/auth/admin/login`. Those two variables are the **bootstrap seed, not the ongoing source of truth**: once the document exists, authentication runs against it. An `admin` is an ordinary account promoted by a super admin (`PATCH /api/v1/admin/users/:studentId/role`).
- **`superadmin` is storable but not assignable.** `ASSIGNABLE_ROLES` omits it, so no API call can mint a second one; the only writer is the bootstrap in `services/rootAdminService.ts`. Do not add an API path to it.
- **Never let `resolveRootSuperadmin()` upgrade an existing account.** It adopts a document only if it *already* holds `superadmin`, and registration refuses `ADMIN_EMAIL` outright. Both halves are needed: without them, anyone who learned the configured address could register it before the first admin sign-in and then authenticate with their own password to be handed the role. This is the escalation the whole bootstrap is shaped around.
- **There is exactly one password check: `authenticateAccount()` in `auth.routes.ts`.** Both sign-in routes go through it, so lockout, account status, email verification and the failure counter are defined once. Do not write a bespoke check for a privileged account — that is precisely where a missing status check goes unnoticed.
- A promoted admin is a `Student` document with `role: 'admin'`, so it keeps its student capabilities. Do not "fix" that by splitting staff into a separate collection without a `DECISIONS.md` entry first — the reuse is the point (see the Milestone 3 ADR).
- Students register via `/api/v1/auth/register` with fullName + mobile + **email** + password. `role` submitted at registration is ignored; the schema default is the only way it is set.
- Students log in with **either** their mobile number or their email (`identifier` field). Email verification is **real** and required before login; the old fake client-side OTP step has been deleted. Do not reintroduce any mock verification.
- **Every account gets a rotating refresh token**, the super admin included. There is no longer a longer-lived admin token and no `ADMIN_TOKEN_TTL`; the `root: true` claim is gone, and `resolveCurrentRole()` has **no exemption** — every privileged request re-reads the role from the database. Do not reintroduce a document-less identity (see the Milestone 11 ADR for the five things the old design could not do).
- **The bootstrap super admin signs in only at `/auth/admin/login`.** `/auth/login` refuses it — *after* verifying the password, so the refusal is not an enumeration oracle pointing at the most privileged account. It is staff: no class, no school, no photo, and the public login form is the most-attacked surface in the product. A *promoted* admin is unaffected and uses `/auth/login` normally.
- **The bootstrap super admin earns no XP.** `grantReward()` refuses it, because every leaderboard aggregates `StudentActivity` and a staff account must never rank above the children who competed. A *promoted* admin does earn — it genuinely registered.
- Registration deliberately does **not** create a session. Don't "helpfully" log the student in on registration.

## Security Rules

- Never hardcode secrets. `JWT_SECRET`, `MONGO_URI`, `ADMIN_EMAIL`, `ADMIN_PASSWORD_HASH`, `FRONTEND_URL` are env-only (see [`ENVIRONMENT_VARIABLES.md`](ENVIRONMENT_VARIABLES.md)).
- Read [`SECURITY.md`](SECURITY.md) before touching auth, query building from `req.query`, or CORS config. The previously-documented issues (unvalidated query construction, permissive CORS fallback, insecure JWT default, missing headers/rate limiting) were **fixed in Milestone 1** — don't reintroduce those patterns. Still open: **no CSRF tokens** (the top gap, and more pressing now that Milestone 3 added real state-mutating admin routes) and no two-factor auth. Account lockout arrived in Milestone 2; the authorization model was rebuilt in Milestone 3 — read the "Authorization" section of `SECURITY.md` for the role and permission tables before touching either.
- Do not commit `.env` files (already gitignored). Do not weaken the JWT default-secret warning into a silent success.

## Testing Requirements

- The **backend** has a test suite: `vitest` + `supertest`, plus `mongodb-memory-server` for integration tests against a **real** MongoDB — **1097 tests across 30 files** (measured 2026-08-23 after Milestone 21 Phase G; read the number from `npm test`, not from here). Run with `npm test --prefix backend` (from inside `backend/` when offline; see [`TESTING.md`](TESTING.md)). The **frontend** still has none. See [`TESTING.md`](TESTING.md).
- `NODE_ENV=test` skips `.env` loading, so tests can never pick up real secrets, and also lowers bcrypt cost and disables rate limiters for speed/determinism. Don't "fix" any of that.
- **The Gemini tests must never touch the network.** `setGeminiClientFactory()` in `services/geminiQuestionGenerator.ts` swaps the whole SDK client and throws outside the test environment; use it rather than a real key, and note that `enableGemini()` only needs an obviously-fake string because `isAvailable()` merely asks whether a key is present. The failing paths are the ones worth testing — a spent quota, a truncated reply, prose where JSON was asked for — and none of them can be produced on demand against a real provider.
- Use `tests/helpers/db.ts` (real in-memory MongoDB) and `tests/helpers/auth.ts` (`registerVerifyLogin`, cookie parsing, real token extraction from the captured email) rather than writing new harnesses. **`registerVerifyLogin()` grants the entry fee by default** — a student exercising practice in production has paid, and a test student who cannot practise asserts behaviour no real student reaches. Pass `{ paid: false }` where *not* having paid is the point. `createAdminSession()` is deliberately unpaid: staff are not entrants, and an admin with an entry-fee payment would appear in the payments console's collected total.
- **Rate limiting, security headers and CORS are implemented but not asserted by tests.** Absence of a test is not absence of the protection.
- Write assertions that name the status they forbid (`expect(res.status).not.toBe(500)`), not vague ones. A weak `not.toBe(400)` assertion hid a real 500 bug during Milestone 1.
- Adding a frontend test framework requires a `DECISIONS.md` entry first.
